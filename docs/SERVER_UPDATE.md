# Обновление сервера одной командой

Обновление запускается вручную:

```bash
sudo systemctl start reshuffle-update
```

Команда сама получает актуальный `origin/main`, собирает образ, делает резервную копию и проверяет запуск. Таймер, cron и Codex для этого не нужны. После однократной настройки больше не требуется передавать контекст серверному Codex перед каждым релизом.

## Что проверяет обновление

`ops/update_bot.py` использует настройки из отдельного серверного JSON. Он допускает только чистый checkout `main`, сохраняет используемые Compose-файлы, overrides, имя проекта, `.env` и build arguments. Образ кандидата собирается в отдельном Git worktree до остановки работающего бота. Два обновления одновременно не выполняются.

Предварительная проверка сверяет конфигурацию с фактически работающим контейнером: аккаунт Discord, окружение, команду, пользователя и реальные имена/пути томов. Несовпадение требует сначала разобраться с конфигурацией. Дополнительные writable mounts и каталоги read-only bind mounts требуют отдельной стратегии резервного копирования; этот updater их не развёртывает. Каталоги резервных копий и состояния не должны пересекаться с подключёнными томами. Конфиги повторно проверяются перед остановкой и запуском.

Перед заменой контейнера бот останавливается. В приватном каталоге создаётся резервная копия всего `/data`, включая SQLite и файлы конфигурации и авторизации, а также явно указанных конфигурационных файлов хоста. Каждое развёртывание после успешной сборки получает отдельный каталог `дата-SHA` с `data.tar.gz`, копиями серверных файлов и `manifest.json`. При ошибке резервного копирования новая версия не запускается, прежний бот возвращается в работу.

Успешный запуск требует свежего heartbeat нового процесса с ожидаемым SHA, подключения к Discord и, если книжный клуб включён, первого успешного обновления его публикаций. Одного состояния Docker «running» недостаточно. После успеха рабочий checkout переводится вперёд до установленного `main`. Сводка сохраняется в `state_dir/last-report.json`; по умолчанию это `/var/lib/reshuffle-updater/last-report.json`.

Обновление не запускает импорт, `scan`, Codex, модель или авторизацию, не меняет лимиты и счётчики импортера. При активном анализе или применении архивного импорта обновление отклоняется до остановки бота. Обычная работа запущенного бота обновляет его карточки и выполняет уже настроенные задачи. Проверка heartbeat подтверждает успешное обновление публикаций, но не заменяет визуальную проверку конкретных кнопок или закрепа после изменений интерфейса.

Полный набор unit-тестов нужно выполнять до слияния в `main`; сервер проверяет сборку, запуск и сохранность защищённых данных. Сравнение данных консервативное: действие организатора или автоматическая смена статуса во время запуска тоже может дать сообщение об изменении. Тогда сверить отчёт и фактическое состояние, сохранив рабочие данные.

## Однократная настройка на Docker-хосте

Нужны Linux с systemd, Python 3.10+, Git, Docker и Compose v2. Устанавливать службу следует на том же хосте, где работает контейнер. Примеры ниже используют `/srv/reshuffle`; перед выполнением заменить его фактическим путём checkout.

1. Проверить, что работает один экземпляр бота с данным Discord-токеном. Старый дублирующий контейнер оставить выключенным. Зафиксировать текущий SHA, Compose-проект, сервис, все используемые `-f`/override-файлы, `.env`, build arguments и реальный том `/data`. Получить свежий `main` в чистом checkout обычным fast-forward. При локальных изменениях или другой ветке сначала разобрать их; `reset --hard`, `clean` и пересоздание `/data` для настройки не нужны.

2. Создать приватный конфиг вне репозитория:

   ```bash
   sudo install -d -m 0700 /etc/reshuffle
   sudo install -m 0600 /srv/reshuffle/ops/update.example.json /etc/reshuffle/update.json
   sudoedit /etc/reshuffle/update.json
   ```

   Если конфиг уже существует, отредактировать его, сохранив реальные значения; повторное копирование шаблона заменит настройки. В JSON указать:

   | Поле | Значение на сервере |
   | --- | --- |
   | `repo` | Абсолютный путь чистого checkout `main`. |
   | `remote`, `branch` | `origin` и `main`; другой remote допустим только после проверки его адреса. |
   | `service`, `project` | Фактические Compose-сервис и проект; обычно оба `reshuffle`. |
   | `compose_files` | Все фактически используемые Compose-файлы в прежнем порядке, абсолютными путями. Указать и overrides. |
   | `env_file` | Фактический `.env`, абсолютный путь. Секреты остаются в нём. |
   | `backup_dir`, `state_dir` | Приватные каталоги хоста вне checkout и `/data`, по умолчанию `/var/backups/reshuffle` и `/var/lib/reshuffle-updater`. |
   | `database_path` | Путь SQLite внутри контейнера, обычно `/data/voice_activity.sqlite3`. |
   | `health_timeout`, `command_timeout` | Время ожидания запуска и отдельной команды в секундах; по умолчанию 300 и 900. |
   | `build_args` | Фактические аргументы сборки. Если на сервере установлен CLI импортера, сохранить `{"INSTALL_CODEX": "true", "CODEX_VERSION": "0.152.1"}` либо уже выбранную версию. Пустой объект собирает обычный образ без CLI. |
   | `external_config_files` | Абсолютные пути дополнительных серверных конфигов вне `/data`, которые нужны в резервной копии; при отсутствии — `[]`. |
   | `enabled` | Вначале `false`, после успешной предварительной проверки — `true`. Это разрешает ручной запуск, расписания не создаёт. |

   Копия всего `/data` уже содержит конфиги книжного клуба, профиль Codex, завершённые импорты и бюджет. Не дублировать их в Git или в шаблоне конфигурации. Резервные копии автоматически не удаляются: следить за свободным местом и хранением отдельно.

3. Проверить конфигурацию без остановки бота и без обновления:

   ```bash
   sudo /usr/bin/python3 /srv/reshuffle/ops/update_bot.py --config /etc/reshuffle/update.json --check
   ```

   Служба работает от root, поэтому именно root нужен доступ на чтение Git remote, Docker и серверных конфигов. Исправить ошибки доступа до включения обновлений. Не печатать `.env`, полное развёрнутое Compose-окружение и файлы авторизации в отчёт.

4. Установить службу:

   ```bash
   sudo /usr/bin/python3 /srv/reshuffle/ops/install_update_service.py --config /etc/reshuffle/update.json
   ```

   Установщик повторяет `--check`, затем записывает `reshuffle-update.service` и выполняет `daemon-reload`. Он не запускает обновление и не устанавливает расписание. Повторная установка обновляет только свою службу; чужая служба с тем же именем или symlink не заменяется.

5. В конфиге поставить `enabled: true`, сохранив права `0600`. Выполнить первый ручной запуск и проверить результат:

   ```bash
   sudo systemctl start reshuffle-update
   sudo systemctl show reshuffle-update -p Result -p ExecMainStatus
   sudo journalctl -u reshuffle-update -n 100 --no-pager
   sudo cat /var/lib/reshuffle-updater/last-report.json
   ```

   Для успешно завершившейся oneshot-службы ожидаются `Result=success` и `ExecMainStatus=0`; состояние `inactive` после завершения нормально. Путь к отчёту берётся из фактического `state_dir`. Проверить записанные SHA и путь резервной копии, одну работающую копию бота, сохранность статусов/порядка/ID и неизменность бюджета импортера. После релиза интерфейса отдельно открыть текущую книгу, план и архив в Discord.

## Последующие обновления

Выполнять `sudo systemctl start reshuffle-update`. При отсутствии новой версии бот не перезапускается. Прогресс доступен через `sudo journalctl -fu reshuffle-update` в другом терминале. Итог — в журнале службы и `last-report.json`. При ошибке команда завершается неуспешно; сначала прочитать отчёт, затем устранять причину. Не повторять обновление параллельно через ручной `docker compose up`.

Для временной блокировки новых обновлений поставить `enabled: false`; работающий бот продолжит работу. Это не прерывает уже начатое обновление. У службы нет автозапуска при загрузке, таймера или автоматического перезапуска.

## Ошибка запуска и восстановление

Если новый контейнер не прошёл проверку, он останавливается. Прежний образ возвращается автоматически только при неизменившейся схеме SQLite. Если новая версия мигрировала схему, бот остаётся остановленным, а отчёт требует ручного восстановления. Версию с несовместимой схемой нельзя автоматически запустить поверх новой БД.

Если предыдущая версия ещё не поддерживает heartbeat, возврат на неё подтверждает только работающий контейнер. Отчёт отдельно требует ручной проверки Discord. После появления heartbeat следующие откаты проверяют и его.

Резервная копия БД и тома автоматически не накатывается. Уже запущенный кандидат мог отправить сообщения в Discord: слепой возврат старой БД потеряет их привязки и создаст риск дублей. Для ручного восстановления сохранить состояние после сбоя, сопоставить журналы публикаций с Discord и выбрать совместимый код или согласованный откат данных. Старый дублирующий контейнер для этого не запускать.

Служба использует `Type=oneshot`, приватную маску файлов `0077` и отключённый внешний таймаут запуска, чтобы systemd не оборвал резервное копирование или восстановление посередине. Отдельные команды ограничивает сам updater. См. [описание oneshot и TimeoutStartSec](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) и [UMask](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).

## Проверки кода и первая серверная проверка

Полный прогон: `python -m unittest discover -s tests`. Тесты проверяют потерянные ответы Docker, подмену тома и окружения, целостность SQLite, приватность отчётов, сохранность данных и ограничения отката. Docker/Git в сценариях обновления заменены управляемыми тестовыми границами. Саму связку Linux, Docker и systemd нужно проверить при первом серверном запуске по шагам выше; локальный прогон на Windows её не заменяет.
