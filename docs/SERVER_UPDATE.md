# Автоматическое и ручное обновление сервера

После включения автоматического режима изменения `main` устанавливаются без SSH-команды: GitHub Actions запускает тесты и пробную сборку Docker, сервер раз в пять минут проверяет успешный результат для **точного SHA**, затем выполняет существующее обновление с резервной копией и проверкой здоровья. Обычный push в рабочую ветку не обновляет бота; нужно слить изменение в `main` и дождаться CI.

Ручной режим также сохранён:

```bash
sudo systemctl start reshuffle-update
```

Команда сама получает актуальный `origin/main`, собирает образ, делает резервную копию и проверяет запуск. Ручная команда не требует CI и предназначена для осознанного вмешательства оператора. Автоматический режим использует отдельные `reshuffle-auto-update.service` и `.timer`, общий deployment-lock и тот же updater. Codex, GitHub SSH-секреты и входящий webhook на сервере для этого не нужны.

## Включение автоматического режима

Сначала настройте и проверьте ручной updater по разделу ниже. В `/etc/reshuffle/update.json` сохраните реальные Compose overrides, build arguments, каталоги и добавьте `"automatic_enabled": true` при `"enabled": true`. Образец по умолчанию оставляет оба режима выключенными.

Установите timer **тем же Python 3.10+, которым работает существующая служба**:

```bash
sudo systemctl cat reshuffle-update.service
# Возьмите путь Python из ExecStart; системный python3 может быть старее 3.10.
sudo /path/to/python3.12 /srv/reshuffle/ops/install_update_service.py \
  --config /etc/reshuffle/update.json --python /path/to/python3.12 --automatic
sudo systemctl status reshuffle-auto-update.timer --no-pager
```

Замените `/srv/reshuffle` и путь Python фактическими значениями. Установщик проверяет конфигурацию до записи файлов, не заменяет чужие units, затем включает timer с автозапуском после перезагрузки. Первая проверка — примерно через 30 секунд, следующие — через пять минут после завершения предыдущей с небольшим разбросом. Сборка не прерывается новым срабатыванием таймера.

CI определён в `.github/workflows/ci.yml`: Python 3.12, полный unittest-набор, Docker build и проверка импортов от пользователя образа без сети. Actions закреплены SHA, доступ workflow — только чтение репозитория. На production образ строится существующим updater с сохранением фактических серверных build arguments, включая установленный CLI импортера. CI не запускает импорт и не использует токен Discord.

`ops/auto_update.py` читает публичный GitHub API `delta-dashed/DeShuffle` и допускает только завершённый успешный запуск `ci.yml` для `main` и проверяемого commit. Результат PR, другой SHA, другой workflow, пропущенный или отменённый запуск не разрешают deployment. Более новая неудачная попытка не обходится старым успехом. Пока CI идёт либо GitHub недоступен, текущий бот продолжает работу. Если `main` изменился между проверкой CI и повторным fetch, запуск отклоняется до сборки/остановки и проверяется на следующем цикле. Перевод репозитория в private потребует отдельно настроить API-доступ; сейчас никакой GitHub-токен на сервер не копируется.

Прогресс и результат:

```bash
sudo systemctl list-timers reshuffle-auto-update.timer --all
sudo journalctl -u reshuffle-auto-update -n 80 --no-pager
sudo cat /var/lib/reshuffle-updater/automatic-report.json
sudo cat /var/lib/reshuffle-updater/last-report.json
```

`automatic-report.json` показывает `unchanged`, `waiting_ci`, `blocked_ci`, `updated`, `failed` или `blocked_release`, SHA и ссылку на CI. `last-report.json` содержит подробности последнего deployment и путь резервной копии. Неизменённый commit не пересобирается и не перезапускается. При ошибке/обрыве deployment тот же SHA блокируется, чтобы timer не повторял каждые пять минут остановку бота и создание резервных копий. После выяснения причины можно явно повторить:

```bash
sudo /path/to/python3.12 /srv/reshuffle/ops/auto_update.py \
  --config /etc/reshuffle/update.json --retry-failed
```

Новый SHA проходит новую CI-проверку и может разворачиваться после исправления. Журнал незавершённого deployment сохраняется до явного решения. Ошибки preflight/сети остаются в journal и не затирают этот журнал. Каталоги резервных копий не очищаются автоматически.

Отключение будущих автоматических обновлений: `sudo systemctl disable --now reshuffle-auto-update.timer` и `automatic_enabled: false` в конфиге. Работающий бот продолжает работать; уже начатый deployment не прерывается. `enabled: false` дополнительно запрещает и ручной updater.

## Результат и диагностика в GitHub

После завершения `CI` для `main` запускается workflow **Deployment feedback**. Он создаёт запись в GitHub Deployments (`production`), ожидает результат серверного таймера и проверяет фактически запущенный SHA, свежий heartbeat, Discord и книжный клуб. Зелёная проверка CI и успешное production-развёртывание — отдельные результаты. Workflow не запускает обновление, не меняет контейнеры и не получает доступ к интерактивной оболочке сервера.

В GitHub откройте **Actions → Deployment feedback → нужный запуск**. Краткий результат и диагностический лог находятся в Summary и шаге **Observe deployment and publish status**. Артефакт `deployment-feedback-…` содержит `report.json` и `diagnostics.log` и хранится 30 дней. Запись Deployments содержит ссылку на этот запуск.

В отчёте видны точный SHA, этап ошибки, код завершения команды, известная категория ошибки, строки Dockerfile/исходников из traceback и результат отката. Успешный откат не превращает неудачное развёртывание в успешное. При потере связи workflow повторяет чтение; через 30 минут без подтверждения выставляет ошибку. Более новый `main` помечает пропущенный старый кандидат как `inactive`, а не как успешно установленный.

Для повторной диагностики без SSH: **Actions → Deployment feedback → Run workflow → main → observe**. Это только чтение текущего состояния. Режим **self-test** намеренно ломает сборку крошечного отдельного Docker-контекста (`FROM scratch`, отсутствующий COPY-файл). Он создаёт красный диагностический запуск в отдельном окружении `diagnostics-test`; работающий бот и его данные не затрагиваются. Ожидаемый результат теста — `failure` с этапом `building` и диагностикой Docker.

### Доступ и приватность

Используется отдельный Ed25519 SSH-ключ. Его публичная часть в `/root/.ssh/authorized_keys` обязательно имеет `restrict,command="<PYTHON> <REPO>/ops/deployment_feedback.py --config /etc/reshuffle/update.json"`. Подставьте реальные абсолютные пути, включая Python 3.10+. Команда принимает через `SSH_ORIGINAL_COMMAND` только `report`, `self-test`, `health` и `health-self-test`, за каждым следует один полный 40-символьный SHA; произвольные команды, аргументы, SFTP, PTY и forwarding запрещены. Обычный административный ключ не используется в GitHub.

Три repository Actions Secrets: `DEPLOY_FEEDBACK_HOST` (адрес), `DEPLOY_FEEDBACK_KEY` (отдельный приватный ключ), `DEPLOY_FEEDBACK_KNOWN_HOSTS` (заранее проверенный ключ SSH-хоста). Проверка host key обязательна; при переносе сервера нужно обновить адрес и сверенный ключ хоста. На сервере не хранится GitHub-токен. Workflow использует временный `GITHUB_TOKEN` с `contents: read` и `deployments: write`; запускается только для доверенного `main`, не для PR или форков.

Репозиторий публичный, поэтому произвольный текст ошибок/сообщений бота не выгружается в Actions. Публичная диагностика строится из разрешённых полей и фиксированных категорий, а не заменой известных токенов в сыром логе. Полный исходный вывод сборки и последние 200 строк упавшего контейнера остаются на сервере в `state_dir/logs/<diagnostics_id>/private-output.jsonl` с правами `0600`. Вывод `docker inspect` и конфигурации Compose не записывается в эти логи. Сохраняется до 128 KiB вывода одной команды и примерно 2 MiB за попытку; публичный журнал ограничен 500 событиями. История отчётов по SHA находится в `state_dir/deployments/`. Эти файлы не удаляются автоматически.

Ошибка доступа или публикации отчёта не даёт GitHub ложный статус успеха и не отключает серверный таймер. Для отключения только обратной связи можно отключить workflow и удалить отдельную строку `reshuffle-github-feedback` из `authorized_keys`; обновление бота продолжит работать.

## Периодический мониторинг после запуска

Workflow **Bot health** проверяет работоспособность независимо от развёртываний по расписанию `2-57/5 * * * *` (примерно каждые пять минут). Проверка запускается на GitHub runner, поэтому недоступность самого сервера тоже даёт красный результат. Используется существующий ограниченный SSH-ключ; новые секреты, доступ к shell и GitHub-токен на сервере не нужны. Workflow имеет только `contents: read` и не изменяет статусы Deployments.

Откройте **Actions → Bot health → последний запуск**: Summary и шаг **Check server and bot readiness** показывают время проверки, фактический SHA работающего контейнера, итог и безопасные коды причин. При ошибке сохраняется артефакт `runtime-health-…` с JSON и диагностическим логом на 30 дней. Для проверки прямо сейчас нажмите **Run workflow → main**; ручной запуск сохраняет артефакт и при успехе. Значок в README ведёт к истории проверок. Успешный новый запуск показывает восстановление после предыдущего сбоя.

Монитор смотрит на фактический runtime, а не на последний отчёт об обновлении. Работающая старая версия после отката считается здоровой, даже если новый SHA не развернулся. Проверяются наличие единственного контейнера, его работа, SHA, свежий heartbeat, подключение к Discord и успешная свежая сверка книжного клуба. `unhealthy` означает проблему контейнера/бота; `unavailable` — сервер ответил, но получить или подтвердить диагностику не удалось; `unreachable` — недоступен сервер либо ограниченный SSH-доступ (в том числе проблема ключа/сети). Содержимое сообщений и токены не публикуются.

Перед объявлением сбоя выполняются три попытки с паузой 15 секунд. Если бот перезапускается в рамках текущего обновления, монитор ждёт: для этого должны одновременно существовать активная блокировка updater, фаза `backup`/`deploying` и свежая отметка фазы. Льготное время ограничено; старый JSON не маскирует упавшего бота. Общий предел ожидания проверки — около семи минут, после которого отсутствие подтверждения даёт ошибку. Монитор не перезапускает и не откатывает бот самостоятельно.

**Bot health self-test → Run workflow** проверяет два ожидаемо красных сценария отдельно от production-мониторинга. `unhealthy-test` передаёт синтетический устаревший heartbeat настоящему проверяющему коду, не меняя live-файлы. `unreachable-test` направляет SSH-пробу на закрытый порт 1 loopback-интерфейса GitHub runner, не отключая сервер. Оба проходят обычный путь трёх проб, вывода ошибки и сохранения артефакта; production-контейнер не останавливается.

Ограничение платформы: [GitHub может задерживать или пропускать scheduled runs и отключает расписания публичного репозитория после 60 дней без активности](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule). Это не гарантия обнаружения ровно через пять минут. Смотрите время последней проверки; отключённое расписание включается на странице workflow. Если недоступен сам GitHub, новое состояние там не появится до восстановления платформы. Уведомления о неудачных Actions runs зависят от личных настроек GitHub; отдельные письма или сообщения монитор не отправляет.

## Проверки и сохранность при обновлении

`ops/update_bot.py` использует настройки из отдельного серверного JSON. Он допускает только чистый checkout `main`, сохраняет используемые Compose-файлы, overrides, имя проекта, `.env` и build arguments. Образ кандидата собирается в отдельном Git worktree до остановки работающего бота. Два обновления одновременно не выполняются.

Предварительная проверка сверяет конфигурацию с фактически работающим контейнером: аккаунт Discord, окружение, команду, пользователя и реальные имена/пути томов. Несовпадение требует сначала разобраться с конфигурацией. Дополнительные writable mounts и каталоги read-only bind mounts требуют отдельной стратегии резервного копирования; этот updater их не развёртывает. Каталоги резервных копий и состояния не должны пересекаться с подключёнными томами. Конфиги повторно проверяются перед остановкой и запуском.

Перед заменой контейнера бот останавливается. В приватном каталоге создаётся резервная копия всего `/data`, включая SQLite и файлы конфигурации и авторизации, а также явно указанных конфигурационных файлов хоста. Каждое развёртывание после успешной сборки получает отдельный каталог `дата-SHA` с `data.tar.gz`, копиями серверных файлов и `manifest.json`. При ошибке резервного копирования новая версия не запускается, прежний бот возвращается в работу.

Успешный запуск требует свежего heartbeat нового процесса с ожидаемым SHA, подключения к Discord и, если книжный клуб включён, первого успешного обновления его публикаций. Одного состояния Docker «running» недостаточно. После успеха рабочий checkout переводится вперёд до установленного `main`. Сводка сохраняется в `state_dir/last-report.json`; по умолчанию это `/var/lib/reshuffle-updater/last-report.json`.

Обновление не запускает импорт, `scan`, Codex, модель или авторизацию, не меняет лимиты и счётчики импортера. При активном анализе или применении архивного импорта обновление отклоняется до остановки бота. Обычная работа запущенного бота обновляет его карточки и выполняет уже настроенные задачи. Проверка heartbeat подтверждает успешное обновление публикаций, но не заменяет визуальную проверку конкретных кнопок или закрепа после изменений интерфейса.

Полный набор unit-тестов нужно выполнять до слияния в `main`; сервер проверяет сборку, запуск и сохранность защищённых данных. Сравнение данных консервативное: действие организатора или автоматическая смена статуса во время запуска тоже может дать сообщение об изменении. Тогда сверить отчёт и фактическое состояние, сохранив рабочие данные.

## Однократная настройка на Docker-хосте

Нужны Linux с systemd, Python 3.10+, Git, Docker и Compose v2. Устанавливать службу следует на том же хосте, где работает контейнер. Примеры ниже используют `/srv/reshuffle`; перед выполнением заменить его фактическим путём checkout.

1. Проверить, что работает один экземпляр бота с данным Discord-токеном. Старый дублирующий контейнер оставить выключенным. Зафиксировать текущий SHA, Compose-проект, сервис, все используемые `-f`/override-файлы, `.env`, build arguments и реальный том `/data`. Получить свежий `main` в чистом checkout обычным fast-forward. При локальных изменениях или другой ветке сначала разобрать их; `reset --hard`, `clean` и пересоздание `/data` для настройки не нужны.

2. Создать приватный конфиг вне репозитория:

   ```bash
   sudo install -d -m 0700 /etc/reshuffle
   sudo install -m 0600 /srv/reshuffle/ops/update.example.json /etc/reshuffle/update.json
   sudoedit /etc/reshuffle/update.json
   ```

   Если конфиг уже существует, отредактировать его, сохранив реальные значения; повторное копирование шаблона заменит настройки. В JSON указать:

   | Поле | Значение на сервере |
   | --- | --- |
   | `repo` | Абсолютный путь чистого checkout `main`. |
   | `remote`, `branch` | `origin` и `main`; другой remote допустим только после проверки его адреса. |
   | `service`, `project` | Фактические Compose-сервис и проект; обычно оба `reshuffle`. |
   | `compose_files` | Все фактически используемые Compose-файлы в прежнем порядке, абсолютными путями. Указать и overrides. |
   | `env_file` | Фактический `.env`, абсолютный путь. Секреты остаются в нём. |
   | `backup_dir`, `state_dir` | Приватные каталоги хоста вне checkout и `/data`, по умолчанию `/var/backups/reshuffle` и `/var/lib/reshuffle-updater`. |
   | `database_path` | Путь SQLite внутри контейнера, обычно `/data/voice_activity.sqlite3`. |
   | `health_timeout`, `command_timeout` | Время ожидания запуска и отдельной команды в секундах; по умолчанию 300 и 900. |
   | `build_args` | Фактические аргументы сборки. Если на сервере установлен CLI импортера, сохранить `{"INSTALL_CODEX": "true", "CODEX_VERSION": "0.152.1"}` либо уже выбранную версию. Пустой объект собирает обычный образ без CLI. |
   | `external_config_files` | Абсолютные пути дополнительных серверных конфигов вне `/data`, которые нужны в резервной копии; при отсутствии — `[]`. |
   | `enabled` | Вначале `false`, после успешной предварительной проверки — `true`. Разрешает updater. |
   | `automatic_enabled` | По умолчанию `false`. Для автоматического режима поставить `true` и отдельно установить timer с `--automatic`. |

   Копия всего `/data` уже содержит конфиги книжного клуба, профиль Codex, завершённые импорты и бюджет. Не дублировать их в Git или в шаблоне конфигурации. Резервные копии автоматически не удаляются: следить за свободным местом и хранением отдельно.

3. Проверить конфигурацию без остановки бота и без обновления:

   ```bash
   sudo /usr/bin/python3 /srv/reshuffle/ops/update_bot.py --config /etc/reshuffle/update.json --check
   ```

   Служба работает от root, поэтому именно root нужен доступ на чтение Git remote, Docker и серверных конфигов. Исправить ошибки доступа до включения обновлений. Не печатать `.env`, полное развёрнутое Compose-окружение и файлы авторизации в отчёт.

4. Установить службу:

   ```bash
   sudo /usr/bin/python3 /srv/reshuffle/ops/install_update_service.py --config /etc/reshuffle/update.json
   ```

   Установщик повторяет `--check`, затем записывает `reshuffle-update.service` и выполняет `daemon-reload`. Он не запускает обновление и не устанавливает расписание. Повторная установка обновляет только свою службу; чужая служба с тем же именем или symlink не заменяется.

5. В конфиге поставить `enabled: true`, сохранив права `0600`. Выполнить первый ручной запуск и проверить результат:

   ```bash
   sudo systemctl start reshuffle-update
   sudo systemctl show reshuffle-update -p Result -p ExecMainStatus
   sudo journalctl -u reshuffle-update -n 100 --no-pager
   sudo cat /var/lib/reshuffle-updater/last-report.json
   ```

   Для успешно завершившейся oneshot-службы ожидаются `Result=success` и `ExecMainStatus=0`; состояние `inactive` после завершения нормально. Путь к отчёту берётся из фактического `state_dir`. Проверить записанные SHA и путь резервной копии, одну работающую копию бота, сохранность статусов/порядка/ID и неизменность бюджета импортера. После релиза интерфейса отдельно открыть текущую книгу, план и архив в Discord.

## Последующие обновления

Выполнять `sudo systemctl start reshuffle-update`. При отсутствии новой версии бот не перезапускается. Прогресс доступен через `sudo journalctl -fu reshuffle-update` в другом терминале. Итог — в журнале службы и `last-report.json`. При ошибке команда завершается неуспешно; сначала прочитать отчёт, затем устранять причину. Не повторять обновление параллельно через ручной `docker compose up`.

Для временной блокировки всех новых обновлений поставить `enabled: false`; работающий бот продолжит работу. Это не прерывает уже начатое обновление. Ручная служба сама по себе не имеет расписания; для автоматического режима используются отдельные units, описанные выше.

## Ошибка запуска и восстановление

Если новый контейнер не прошёл проверку, он останавливается. Прежний образ возвращается автоматически только при неизменившейся схеме SQLite. Если новая версия мигрировала схему, бот остаётся остановленным, а отчёт требует ручного восстановления. Версию с несовместимой схемой нельзя автоматически запустить поверх новой БД.

Если предыдущая версия ещё не поддерживает heartbeat, возврат на неё подтверждает только работающий контейнер. Отчёт отдельно требует ручной проверки Discord. После появления heartbeat следующие откаты проверяют и его.

Резервная копия БД и тома автоматически не накатывается. Уже запущенный кандидат мог отправить сообщения в Discord: слепой возврат старой БД потеряет их привязки и создаст риск дублей. Для ручного восстановления сохранить состояние после сбоя, сопоставить журналы публикаций с Discord и выбрать совместимый код или согласованный откат данных. Старый дублирующий контейнер для этого не запускать.

Служба использует `Type=oneshot`, приватную маску файлов `0077` и отключённый внешний таймаут запуска, чтобы systemd не оборвал резервное копирование или восстановление посередине. Отдельные команды ограничивает сам updater. См. [описание oneshot и TimeoutStartSec](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) и [UMask](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).

## Проверки кода и первая серверная проверка

Полный прогон: `python -m unittest discover -s tests`. Тесты проверяют потерянные ответы Docker, подмену тома и окружения, целостность SQLite, приватность отчётов, сохранность данных и ограничения отката. Docker/Git в сценариях обновления заменены управляемыми тестовыми границами. Саму связку Linux, Docker и systemd нужно проверить при первом серверном запуске по шагам выше; локальный прогон на Windows её не заменяет.
